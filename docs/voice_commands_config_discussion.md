# Обсуждение идеи вынести голосовые команды и синонимы в конфигурационный файл

- Статус документа: аналитический отчёт, код пока не менялся.
- Цель: оценить, стоит ли объединить голосовые команды и синонимы в отдельный редактируемый пользователем конфиг.
- Контекст проекта:
  - Активный реестр команд сейчас создаётся в `commands/registry.py` через `build_default_registry()`.
  - Синонимы сейчас заданы как class-level `synonyms` внутри классов в `commands/*.py`.
  - Матчинг выполняется в `commands/router.py`: нормализация, удаление ведущего wake-word, точное совпадение или prefix-match.
  - Тестовый snapshot хранится в `tests/fixtures/commands_snapshot.json`.
  - Уже существует отдельный пользовательский конфиг `settings.toml` и пример `settings.toml.example`.
  - Уже существует похожая, но более узкая система подсказок `config/wake_hints.example.json`; она не управляет реальными командами, только отображением.

## Краткий вывод

- Идея целесообразна, но только в гибридном виде.
- Не стоит выносить поведение команд в конфиг. Исполнение должно остаться в Python-классах.
- Стоит вынести пользовательски редактируемый слой:
  - включена ли команда;
  - список дополнительных синонимов;
  - переопределение или дополнение встроенных синонимов;
  - отображаемое имя/подсказка для UI;
  - порядок показа в wake-hint;
  - возможно, пользовательские категории.
- Лучший вариант для этого проекта: `config/voice_commands.toml` или `commands.toml` с Pydantic-валидацией.
- JSON менее удобен пользователю из-за отсутствия комментариев.
- YAML удобен для ручного редактирования, но добавляет зависимость и больше неоднозначностей.
- Полностью переносить все команды в один внешний файл рискованно: можно легко сломать маршрутизацию, потерять связь с классами команд и усложнить тесты.

## Участники дискуссии

- Эксперт 1: архитектор backend/Python.
- Эксперт 2: UX-инженер и владелец пользовательской настройки.
- Эксперт 3: QA/надёжность, отвечает за тестируемость, совместимость и диагностику.

## Мнение эксперта 1: архитектор backend/Python

- Основная позиция:
  - Выносить синонимы в конфиг полезно, но команды должны остаться кодовыми объектами.
  - Команда — это не только фраза, а контракт: `name`, `command_type`, `ack_before`, `ack_after`, `execute()`, зависимости от pipeline.
  - Конфиг должен ссылаться на стабильный `command.name`, а не определять произвольное поведение.

- Что поддерживает:
  - Встроенные дефолты остаются в классах команд.
  - Внешний конфиг накладывается поверх дефолтов при сборке реестра.
  - Если конфиг отсутствует, приложение работает как сейчас.
  - Если конфиг повреждён, приложение должно показать ошибку и безопасно откатиться к дефолтам или не стартовать в строгом режиме.

- Что считает опасным:
  - Полностью генерировать команды из конфига.
  - Хранить в конфиге Python-имена классов как пользовательскую поверхность.
  - Позволять пользователю менять `command_type` без понимания последствий.
  - Разрешать односоставные команды.
  - Разрешать одинаковый синоним у двух команд без явной ошибки.

- Рекомендованная архитектура:
  - Добавить модель `VoiceCommandConfig`.
  - Добавить загрузчик, например `commands/config_loader.py`.
  - В `build_default_registry()` сначала создать кодовые команды, затем применить overlay из конфига.
  - В `BaseCommand` не обязательно менять интерфейс радикально; можно перед регистрацией оборачивать или копировать список `synonyms`.

## Мнение эксперта 2: UX и пользовательское редактирование

- Основная позиция:
  - Для пользователя важно не «где класс Python», а «какие фразы можно произносить».
  - Конфиг должен быть понятен без знания кода.
  - Нужны комментарии и примеры прямо в файле.

- Что поддерживает:
  - Отдельный файл `config/voice_commands.toml`.
  - Пример `config/voice_commands.example.toml`.
  - Возможность добавлять только свои синонимы, не копируя весь список.
  - Возможность отключить ненужную команду.
  - Возможность поменять текст подсказки wake-hint.

- Предлагаемый UX:
  - Пользователь редактирует секцию:

```toml
[commands.pause]
enabled = true
mode = "extend"
synonyms = [
  "поставь фильм на паузу",
  "приостанови видео",
]
hint = "пауза"
show_in_hints = true
order = 4
```

- Варианты `mode`:
  - `extend` — добавить синонимы к встроенным. Лучший дефолт.
  - `replace` — полностью заменить встроенные синонимы. Только для продвинутых пользователей.
  - `disable` или `enabled = false` — выключить команду.

- Что важно для удобства:
  - Чётко писать, что каждый синоним должен быть минимум из двух слов.
  - Показывать пользователю понятную ошибку: «синоним уже используется командой X».
  - Не заставлять редактировать JSON snapshot вручную для обычного пользователя.
  - Желательно дать CLI-команду проверки: `python -m scripts.validate_voice_commands_config`.

## Мнение эксперта 3: QA, тестируемость и надёжность

- Основная позиция:
  - Идея хорошая, если ввести строгую валидацию и предсказуемое поведение при ошибках.
  - Без тестов такая миграция опасна: команды — центральная часть UX.

- Главные риски:
  - Пользователь добавит синоним из одного слова, и возрастут ложные срабатывания.
  - Пользователь добавит одинаковую фразу в две команды.
  - Пользователь случайно отключит `stop` и не сможет голосом выключить дежурный режим.
  - Пользователь заменит синонимы content-команды и сломает привычный сценарий диктовки.
  - Snapshot-тесты начнут зависеть от локального пользовательского конфига.
  - Wake-hint и реальный реестр снова разъедутся.

- Требования QA:
  - Тесты дефолтного реестра должны игнорировать пользовательский `config/voice_commands.toml`.
  - Должен быть отдельный набор тестов для overlay-конфига.
  - Нужны тесты на:
    - `extend`;
    - `replace`;
    - `enabled = false`;
    - неизвестное имя команды;
    - пустой список синонимов;
    - односоставный синоним;
    - дубликат внутри одной команды;
    - дубликат между разными командами;
    - конфликт длинного и короткого синонима;
    - сохранение приоритета `GLOBAL`.
  - Нужен лог итогового реестра при старте: сколько команд, сколько синонимов, сколько пользовательских.

## Варианты объединения команд и синонимов

### Вариант A: оставить всё как есть

- Описание:
  - Синонимы остаются в Python-классах.
  - Текстовый справочник обновляется вручную.

- Плюсы:
  - Минимальная сложность.
  - Максимальная предсказуемость.
  - Текущие тесты и архитектура почти не меняются.

- Минусы:
  - Пользователю неудобно редактировать фразы.
  - Любая правка требует знания Python.
  - Высокий риск забыть обновить справочник, wake-hint или snapshot.

- Оценка:
  - Хорошо для разработки.
  - Плохо для пользовательской настройки.

### Вариант B: полностью перенести все команды и синонимы в один конфиг

- Описание:
  - Конфиг содержит все команды, типы, синонимы, ack-файлы, классы обработчиков.
  - Реестр строится почти целиком из конфига.

- Плюсы:
  - Всё видно в одном месте.
  - Пользователь может редактировать полный список.
  - Можно генерировать документацию и wake-hint из одного файла.

- Минусы:
  - Конфиг начинает описывать не только данные, но и архитектуру.
  - Ошибка в конфиге может сломать запуск.
  - Появляется необходимость связывать строку `handler` с Python-классом.
  - Сложнее поддерживать миграции.
  - Пользователь может случайно изменить технические поля.
  - Повышается риск рассинхронизации между кодом и конфигом.

- Оценка:
  - Не рекомендуется как первый шаг.
  - Возможен только если в будущем появится полноценная plugin-система команд.

### Вариант C: внешний overlay-конфиг поверх кодовых дефолтов

- Описание:
  - Python-классы остаются источником поведения и базовых дефолтов.
  - Внешний файл хранит пользовательские изменения.
  - Конфиг может расширять, заменять или отключать синонимы.

- Плюсы:
  - Хороший баланс удобства и надёжности.
  - Без конфига приложение работает как сейчас.
  - Можно валидировать только пользовательский слой.
  - Меньше шансов сломать поведение команд.
  - Легко мигрировать постепенно.

- Минусы:
  - Источник истины становится двухслойным: кодовые дефолты + overlay.
  - Нужно явно объяснить пользователю `extend` и `replace`.
  - Тесты должны различать дефолтный и пользовательский режим.

- Оценка:
  - Рекомендуемый вариант.

### Вариант D: вынести только синонимы, но не metadata

- Описание:
  - Конфиг содержит только списки фраз по `command.name`.
  - `enabled`, `hint`, `order` остаются в других местах.

- Плюсы:
  - Минимальный конфиг.
  - Меньше риска испортить технические параметры.

- Минусы:
  - Wake-hint продолжит жить отдельно.
  - Пользователь всё равно не сможет отключить команду.
  - Со временем появится второй/третий конфиг для связанных настроек.

- Оценка:
  - Лучше, чем ничего, но слабее варианта C.

### Вариант E: объединить real commands и wake-hints в один конфиг

- Описание:
  - Один файл управляет и реальным реестром, и отображением подсказок.

- Плюсы:
  - Нет рассинхронизации между реальными командами и подсказкой.
  - Пользователь редактирует один файл.

- Минусы:
  - Нужно аккуратно разделить поля «исполнение» и «отображение».
  - Нельзя допустить, чтобы скрытие из подсказок отключало команду, если пользователь этого не ожидал.

- Оценка:
  - Хорошее развитие варианта C.
  - Рекомендуется включить в проектирование сразу, но внедрять осторожно.

## Формат конфигурационного файла

### JSON

- Плюсы:
  - Уже используется для `config/wake_hints.example.json`.
  - Стандартная библиотека Python умеет читать JSON.
  - Удобен для машинной генерации.

- Минусы:
  - Нет комментариев.
  - Неудобен для ручного редактирования длинных списков.
  - Запятые часто ломают файл.
  - Для пользовательского конфига хуже TOML/YAML.

- Вердикт:
  - Подходит для snapshot и внутренних данных.
  - Не лучший выбор для пользовательского редактирования команд.

### TOML

- Плюсы:
  - Уже используется в проекте (`settings.toml`, `settings.toml.example`).
  - Уже есть зависимости `tomli` и `tomli-w`.
  - Поддерживает комментарии.
  - Хорошо читается пользователем.
  - Удобен для секций `[commands.pause]`.

- Минусы:
  - Длинные списки строк выглядят чуть тяжелее, чем в YAML.
  - Требует аккуратной структуры для nested-секций.

- Вердикт:
  - Лучший вариант для этого проекта.

### YAML

- Плюсы:
  - Очень удобен для ручных списков.
  - Хорошо подходит для древовидной структуры.

- Минусы:
  - Нужна новая зависимость.
  - YAML имеет неоднозначности типов.
  - Ошибки отступов могут быть менее очевидны.
  - Для проекта, где уже есть TOML, это новый формат без необходимости.

- Вердикт:
  - Хороший формат вообще, но не лучший для текущего проекта.

### Python-файл как конфиг

- Плюсы:
  - Максимальная гибкость.
  - Можно импортировать напрямую.

- Минусы:
  - Небезопасно.
  - Пользовательский файл выполняет код.
  - Сложно валидировать и поддерживать.

- Вердикт:
  - Не использовать.

## Рекомендуемая структура TOML

- Файл по умолчанию:
  - `config/voice_commands.example.toml` — пример, хранится в git.
  - `config/voice_commands.toml` — пользовательский файл, может быть не в git.

- Минимальная структура:

```toml
version = 1

[commands.pause]
enabled = true
mode = "extend"
synonyms = [
  "поставь фильм на паузу",
  "приостанови видео",
]
hint = "пауза"
show_in_hints = true
order = 4
```

- Поля:
  - `version`:
    - версия схемы файла;
    - нужна для будущих миграций.
  - `[commands.<name>]`:
    - `<name>` должен совпадать с `BaseCommand.name`.
  - `enabled`:
    - `true` по умолчанию;
    - `false` исключает команду из реестра.
  - `mode`:
    - `extend` — добавить синонимы к кодовым дефолтам;
    - `replace` — заменить дефолтные синонимы;
    - возможно, `default` — ничего не менять, только metadata для hints.
  - `synonyms`:
    - список пользовательских фраз;
    - каждая фраза минимум из двух слов после нормализации.
  - `hint`:
    - короткая подпись для wake-hint.
  - `show_in_hints`:
    - показывать ли команду в подсказке.
  - `order`:
    - порядок отображения в подсказке.
  - `notes` или комментарии:
    - только для пользователя, приложением игнорируется.

## Альтернативная структура с разделением дефолтов и пользовательских правок

- Более строгий вариант:

```toml
version = 1

[overrides.pause]
append = [
  "поставь фильм на паузу",
  "приостанови видео",
]
remove = [
  "сделай паузу",
]

[hints.pause]
label = "пауза"
show = true
order = 4
```

- Плюсы:
  - Явно видно, что пользователь не переписывает всю команду.
  - Можно удалять отдельные встроенные синонимы.

- Минусы:
  - Сложнее для пользователя.
  - Нужно объяснять `append` и `remove`.

- Вердикт:
  - Хорошо для продвинутого режима.
  - Для первой версии лучше `mode = "extend" | "replace"`.

## Какие изменения потребуются в исходных файлах

- `commands/base.py`:
  - Оставить `BaseCommand` как контракт поведения.
  - Возможное изменение: разрешить создавать runtime-копию команды с изменёнными `synonyms`.
  - Альтернатива: не менять `BaseCommand`, а мутировать `command.synonyms` у экземпляра при сборке реестра. Это проще, но менее чисто.

- `commands/registry.py`:
  - Разделить сборку дефолтного реестра и применение пользовательского overlay.
  - Добавить режимы:
    - `build_default_registry()` — чистый кодовый дефолт, нужен тестам.
    - `build_configured_registry()` — дефолт + `voice_commands.toml`.
  - Или добавить параметр:
    - `build_default_registry(apply_user_config: bool = False)`.
  - Лучший вариант: отдельная функция, чтобы тесты и runtime были явно различимы.

- `commands/router.py`:
  - Больших изменений не нужно.
  - Нужно убедиться, что пары синонимов строятся после применения overlay.
  - Желательно добавить диагностику конфликтов до создания router.

- Новый файл `commands/config_loader.py`:
  - Загрузка `config/voice_commands.toml`.
  - Pydantic-модели схемы.
  - Валидация unknown command names.
  - Валидация синонимов через `commands.router.normalize`.
  - Обнаружение дублей и конфликтов.
  - Применение `extend`/`replace`/`enabled`.

- `config_model.py`:
  - Добавить путь `voice_commands_file`.
  - Возможно добавить флаг `commands.strict_config`.
  - Возможно добавить флаг `commands.allow_disable_global`.

- `config.py`:
  - Пробросить новые настройки как module-level константы, если сохраняется текущий shim-стиль.

- `settings.toml.example`:
  - Добавить путь к файлу команд.
  - Добавить комментарий, что сами команды редактируются в `config/voice_commands.toml`.

- `config/voice_commands.example.toml`:
  - Новый пример пользовательского файла.
  - Включить все команды с закомментированными примерами.
  - Объяснить минимум два слова и режимы `extend`/`replace`.

- `commands/hint_provider.py`:
  - Перевести wake-hints на использование нового command-config metadata.
  - Сохранить обратную совместимость с `config/wake_hints.json` на переходный период.
  - Определить приоритет:
    - новый `voice_commands.toml`;
    - старый `wake_hints.json`;
    - auto-generated fallback из реестра.

- `config/wake_hints.example.json`:
  - После внедрения можно оставить deprecated.
  - Или заменить ссылкой на `config/voice_commands.example.toml`.

- `tests/fixtures/commands_snapshot.json`:
  - Должен фиксировать дефолтный реестр без пользовательского конфига.
  - Возможно добавить второй snapshot для example-конфига.

- `tests/test_commands_registry.py`:
  - Обновить текущий snapshot, который уже сейчас отстаёт от `translate_video`.
  - Добавить тесты на configured registry.

- Новый тестовый файл `tests/test_voice_commands_config.py`:
  - Проверка схемы.
  - Проверка ошибок.
  - Проверка extend/replace/disable.
  - Проверка конфликтов.

- `Полный список голосовых команд.txt`:
  - После внедрения должен указывать, что реальный пользовательский слой хранится в `config/voice_commands.toml`.
  - Можно добавить команду/скрипт генерации этого файла из реестра.

- Новый скрипт `scripts/dump_voice_commands.py`:
  - Генерирует человекочитаемый список команд из текущего configured registry.
  - Поможет избежать ручной рассинхронизации справочника.

- Новый скрипт `scripts/validate_voice_commands_config.py`:
  - Проверяет пользовательский конфиг без запуска всего приложения.
  - Выводит понятные ошибки.

## Валидация и правила безопасности

- Обязательные правила:
  - Все синонимы после нормализации должны содержать минимум два слова.
  - Пустые строки запрещены.
  - Дубликаты внутри одной команды запрещены.
  - Один и тот же нормализованный синоним у разных команд запрещён.
  - Unknown command name в конфиге должен быть ошибкой или предупреждением в зависимости от режима.
  - Команда после `replace` не должна остаться без синонимов.
  - `GLOBAL`-команды должны сохранять приоритет.

- Спорное правило:
  - Разрешать ли отключение `stop`.
  - Рекомендация:
    - по умолчанию не разрешать отключать `stop`;
    - разрешить только через явный advanced-флаг, например `allow_disable_global = true`.

- Нормализация:
  - Валидировать нужно тем же `normalize()`, который использует router.
  - Иначе пользователь увидит один синоним, а router будет сравнивать другой.

- Диагностика:
  - При старте логировать:
    - путь конфига;
    - применён ли конфиг;
    - количество команд;
    - количество дефолтных синонимов;
    - количество пользовательских синонимов;
    - отключённые команды;
    - предупреждения.

## Подводные камни

- Двухслойный источник истины:
  - Кодовые дефолты и пользовательский overlay могут путать разработчика.
  - Нужно явно назвать слои: default registry и configured registry.

- Сломанные локальные конфиги:
  - Пользователь может оставить незакрытую кавычку или неправильный список.
  - Нужен понятный fail-fast или fallback.
  - Для GUI желательно показывать ошибку в UI, а не только в лог.

- Snapshot-тесты:
  - Нельзя, чтобы локальный `config/voice_commands.toml` ломал CI.
  - Тесты дефолта должны использовать чистый режим.

- Wake-hint:
  - Сейчас есть отдельный файл `config/wake_hints.example.json`.
  - Если его не интегрировать, будет два места редактирования.
  - Рекомендация: постепенно объединить hints с voice command config.

- Приоритеты и пересечения:
  - Router выбирает длиннейший синоним, а `GLOBAL` проверяет первым.
  - При пользовательских синонимах надо заранее ловить конфликты, а не надеяться на порядок.

- Content-команды:
  - Для `note`, `question`, `reminder` синоним — только триггер.
  - Тело команды остаётся отдельной речью или хвостом после триггера.
  - Пользователь может ожидать, что добавление «напомни через» как синонима решит парсинг, но это может конфликтовать с текущей логикой `ReminderCommand`.

- Локализация:
  - Сейчас команды русскоязычные.
  - Конфиг должен не ломать кириллицу.
  - TOML-файл нужно читать и писать в UTF-8.

- Версионирование:
  - Без `version` будет сложнее менять формат.
  - Нужно сразу добавить `version = 1`.

- Безопасность:
  - Конфиг не должен содержать исполняемый код.
  - Не использовать Python-конфиг.
  - Не принимать произвольные import paths из пользовательского файла.

- Производительность:
  - На старте будет дополнительная загрузка и валидация.
  - На runtime это почти не влияет, потому что router всё равно строит пары заранее.

- Горячая перезагрузка:
  - В tray уже есть пункт «Перезагрузить конфиг», но сейчас это заглушка.
  - Горячая перезагрузка команд возможна, но требует аккуратно пересоздать registry/router и обновить wake-hint.
  - Для первой версии лучше перезапуск приложения после изменения файла.

## Предлагаемые решения

- Принять гибридный подход:
  - Python-классы остаются владельцами поведения.
  - TOML-конфиг становится пользовательским overlay для синонимов и подсказок.

- Использовать TOML:
  - `config/voice_commands.example.toml` в git;
  - `config/voice_commands.toml` как пользовательский файл.

- Поддержать в первой версии:
  - `enabled`;
  - `mode = "extend" | "replace"`;
  - `synonyms`;
  - `hint`;
  - `show_in_hints`;
  - `order`.

- Не поддерживать в первой версии:
  - создание полностью новых команд без Python-класса;
  - изменение `command_type` через конфиг;
  - изменение `ack_before`/`ack_after` через конфиг;
  - hot reload без перезапуска;
  - произвольные обработчики из конфига.

- Защитить критичные команды:
  - `stop` не отключать без advanced-флага.
  - `GLOBAL`-приоритет не менять через конфиг.

- Сделать валидацию обязательной:
  - односоставные синонимы запрещены;
  - дубликаты запрещены;
  - неизвестные команды диагностируются;
  - пустые списки после `replace` запрещены.

- Синхронизировать подсказки:
  - Новый voice command config должен стать источником для wake-hint.
  - Старый `wake_hints.json` временно поддержать как legacy.

## Итоговая рекомендация трёх экспертов

- Идею стоит реализовывать.
- Делать это нужно не как полный перенос команд в конфиг, а как пользовательский overlay поверх Python-дефолтов.
- Наиболее подходящий формат для проекта — TOML.
- Первый релиз должен быть консервативным:
  - добавление/замена синонимов;
  - отключение обычных команд;
  - управление подсказками;
  - строгая валидация.
- Поведение команд, тип команды, ack-файлы и обработчики должны остаться в коде.
- Главный технический приоритет — не удобство любой ценой, а сохранение предсказуемого и тестируемого voice UX.
